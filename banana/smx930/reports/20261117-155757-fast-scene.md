# Samsung SM-X930 / Mali-G925 — 15:57:57 movie-skip + legacy command-pool test

**Source:** user-private `0400486024DEC000-20261117-155757.log` (883 lines) and matching digest. PanVK faux123 v1.1.8, Banana Native experimental v0.12.1, OoT Switch 2 Edition 131072. **No private raw log or copyrighted game content included in this report.**

## Verified outcomes

- `DM_MOVIE_SKIP=1` was applied. The AV1 decoder explicitly ended after **packet 5**, with end-of-stream reported after five decoded pictures. The test reached the first large 3D render at approximately **35 seconds of observed game/log time** rather than the unskippable full opening movie. This can remain in the fast diagnostic profile (it changes startup workload, so comparisons with full-movie runs are not fully controlled).
- `DM_VK_PREWARM=0` remained applied; no prewarming progress is shown. The original translated 42,848-shader library is still loaded, not retranslated.
- `DM_VK_SLOT_POOL=0` is the effective environment setting, and the native `Mali command pools: one pool per completed replay slot` activation message seen in earlier runs is absent here. Source `vka_exec.c` checks the flag with `VKA_ENV` and falls back to the original pool when zero. The launcher emits `[RED] ... not a switch of this build`; this **appears to be an outdated whitelist/validation warning**, not evidence the native override was ignored. Definitive runtime selection would require a log line for the legacy path.
- Termination recurred. The launcher digest calls it **out of memory**, but no Android `lmkd`, `ApplicationExitInfo`, or tombstone identifying the actual process-kill reason was supplied.

## New highest-return engineering target

The final `pace cost` row at frame 852 reports **352.6 ms per frame** replay recording, of which **272.7 ms** is drawing. Its 1-in-16 draw profiler sample reports **265.49 μs/draw**, including **253.32 μs/draw** in `images+pass+key` (resource resolution, pass transition, render target/image work). That is ~95% of the sampled per-draw path, and is much more expensive than the actual draw command or pipeline lookup. This profiler sample is indicative, not a precise population-wide mean; it cannot be multiplied into a guaranteed improvement.

Primary code: `dm/gfx/vk_android/vka_draw.c` `draw_body()` after `PT(2)` (`walk_all`, `make_images`, image hazards, render-pass checks and pipeline key construction); investigate cacheability of stable descriptors/image state and avoid repeated pass/image preparation **without changing resource dependencies**. Secondary: `vka_tex.c` GPU-written image lifetime and 12,288×12,288 297 MiB image; `vka_mem.c` guest pool backing and VMA pressure. Third: Vulkan queue/fence submissions (6–10 ms/frame), now markedly smaller than first-scene draw preparation.

Other observed pressure: 3 GiB file-backed guest-pool ranges reported during setup, the 297 MiB 12,288×12,288 depth/render image, a 1.89-second graphics pipeline compile during heavy transition, ~35k VMAs (54% of assumed default limit) and MemAvailable falling to 1.5 GiB. The large image is an intentional game render target in prior upstream docs, not evidence of a leak by itself.

## Decision

1. **Keep `DM_MOVIE_SKIP=1` for all short crash reproductions**; preserve prepared shader library and existing pipeline cache.
2. Leave `DM_VK_PREWARM=0`, and don't waste another extended user test simply toggling the slot pool. No stable rendering improvement has been demonstrated from this MassOpt feature.
3. Next development task: source-level audit and instrumentation for `images+pass+key`, then lower peak GPU memory/resident pool pressure. Do not blindly cap images/disable texture dependencies; correctness and scene quality matter.
4. For a definitive Android kill reason, collect `lmkd` / ActivityManager process-exit information through the previously prepared ADB collector. The game log and launcher digest are insufficient to confirm the mechanism. No APK rebuild is necessary to interpret this run.
