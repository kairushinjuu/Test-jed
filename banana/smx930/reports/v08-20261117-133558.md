## Ranked hypotheses — to test, not established fixes

1. **Driver timeline/queue synchronization:** on PanVK the replay thread spends ~9–12 ms per frame in Vulkan queue submission; occasional waits reach 1.3 seconds. The host already supports `DM_VK_TL_HOST=1` to signal timeline values from a fence-completion worker. This is documented in `vka_dev.c`, but might improve or worsen the PanVK driver. A/B first.
2. **PCM underruns caused by producer-side stalls:** Audio rendering itself averages only ~0.1–0.15 ms, but the AAudio consumer runs out of queued audio. Test a modest buffer increase separately using `DM_DBG_AU_FRAMES=5760`, verify requested *and actual* frames in log, and check whether larger latency harms lip-sync. Buffer growth will not fix a 1.3-second stall by itself.
3. **Video packet and transition flow:** the log contains initial AV1 `packet refused (busy)` notices and a second AV1 stream starts later. The source exposes `DM_CODEC_STATS=1` for detailed decoder/picture-gap sampling; enable it in both A and B. The refused events are not proof that the hardware decoder is slow; they can reflect a full input queue.
